// 02 — platform surface

Nine resources. Zero mystery.

Charges & Intents

One-call charges for simple checkouts, PaymentIntents for flows needing 3DS or step-up auth. Minor-unit math everywhere — no floating-point surprises.

POST /v1/charges

Unified ledger

Every movement — auth, capture, refund, dispute, fee — is a row in one append-only ledger. Reconciliation stops being a monthly archaeology dig.

GET /v1/ledger?since=…

SDKs that mirror the API

TypeScript, Python, Go, Ruby, PHP. Identical resource names across languages so a backend swap doesn't rewrite your mental model.

npm i @finpulse/sdk

Webhooks with replay

Signed, ordered per-object, and re-playable from the dashboard for 72 hours. Missed events stop being a support ticket.

Sandbox parity

The sandbox runs the same state machine as the design target for production — same errors, same latency histograms, same test card matrix.

Payouts, scheduled

Daily, weekly, or rolling with a visible settlement calendar per currency. Every payout links back to the exact ledger rows funding it.

// 03 — request anatomy

What happens between “Pay now” and “settled”

  1. 01

    Tokenize at the edge

    Card data never touches your server. The client SDK swaps the PAN for a single-use token in your user's browser region.

    ≈12ms
  2. 02

    Authorize

    FinPulse routes the intent to the issuer, applies your risk rules synchronously, and returns an outcome: settled, review, or declined — with a reason code a human can read.

    ≈78ms
  3. 03

    Ledger + webhook

    The outcome is written to the append-only ledger and pushed to your endpoint, signed, within the same second. Your dashboard is already showing it.

    ≈8ms
  4. 04

    Settle & payout

    Captured funds follow the settlement calendar for their currency. Each payout arrives with a CSV of the ledger rows behind it.

    T+1 (modeled)

// 05 — honest questions

FAQ

Is FinPulse a real payment provider?

No — this is a studio concept build. The dashboards, latency figures, and pricing are design exercises using clearly-labeled sample data. No money moves anywhere.

Why show latencies at all if they're fictional?

Because the point of the concept is that payment UIs should be honest about time. Every number here is labeled as a design target or sample value, and the ticker explicitly says “LIVE SANDBOX / SAMPLE DATA”.

What was the hardest part to design?

The decline state. Everyone designs success screens; a ledger-first dashboard has to make failure readable — reason codes, retry paths, and review queues in the same visual weight as settled payments.

How is the dashboard built?

Pure HTML and CSS — glassmorphic panels are layered backdrop-filter surfaces, the chart is inline SVG, and the table filter uses ~30 lines of vanilla JS. No frameworks, no chart libraries.

Can I reuse the design approach?

The source is public on GitHub — study it, fork it, adapt it. If you build something adjacent, the agency would like to hear about it.
